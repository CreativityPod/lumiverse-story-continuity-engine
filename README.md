# Story Continuity Engine

Persistent character and world state for any character card. Version **1.7.3** is a separate Lumiverse Spindle extension with its own **Story Continuity** drawer, backend storage, and `story_continuity.*` chat variables.

## Install

1. Extract `release/Story_Continuity_Engine_v1.7.3.zip` into your Lumiverse `data/extensions` directory. The archive contains the top-level `lumiverse-story-continuity-engine/` folder with `spindle.json` and ready-to-run `dist` entries. Use Lumiverse's local extension discovery/reload workflow for that installation.
2. Grant **generation**, **interceptor**, **chat_mutation**, **characters**, and **chats**. These support quiet tracker calls, prompt injection, chat-variable mirrors, and card/chat reads. Grant **world_books** to include enabled constant entries from attached lorebooks and **ui_panels** for the floating widget. This extension does not modify character cards or lorebooks.
3. Open an ordinary character chat. Choose **Import Saved Setup** or **Create From Character Card** beneath the opening message, or use the matching controls in the **Story Continuity** drawer. A new chat is recommended for the first run.
4. Optionally select a tracker connection and structured-output mode, then select **Save Settings**. Without a selection, the host's default connection is used.

Built entries are included; installation does not require npm or the development dependencies. The implementation targets the local Lumiverse 1.1.6 APIs. A public repository has not been created or published.

## How it works

The engine reads each card in the chat or group: name, description, personality, scenario, example dialogue, creator notes, and the actual selected opening. The selected opening takes priority over the default greeting. Unselected alternate greetings and system/post-history instructions are not turned into story facts. Example dialogue and creator notes are guidance, not completed history.

A quiet LLM call extracts a structured baseline. Complete bounded card source text is saved alongside the extracted state. The original card remains the host's characterization source. The engine separates stable profiles and appearance from current visible and internal state, keeps recurring identities persistent, and leaves unsupported facts as `Unknown` except for the starting scene defaults below.

When creating from a card, the model extracts **date, time, and weather** from the card, selected opening and lore first. Extracted values take priority, including approximate dates/times, fictional calendars and an explicit absence of ordinary weather. A partial value already counts as established: a missing year, minute or temperature is not filled into it. For wholly missing fields, the same extraction call chooses **coherent starting conditions together**, fitting the established era, calendar, location, climate, season, opening activity and time of day. This applies even with the optional scene-details checkbox off.

Missing weather receives a concise contextual description of relevant warmth/cold, clouds or precipitation, and wind. An approximate temperature is optional when supported by the setting. Indoor scenes distinguish outside conditions from their relevance indoors; sealed or airless settings can explicitly have no ordinary weather. Unknown environments use modest conditions without asserting unsupported geography, season, daylight or climate. Existing weather is preserved even when brief. The model does not invent forecasts or future weather events. These are fictional starting choices, not live weather data.

The backend still saves random fictional **anchors and safety defaults** before extraction: a date from **2020–2039**, a time from **00:00–23:59**, and one of **Clear skies**, **Partly cloudy**, **Overcast**, **Light rain**, or **Light breeze and dry skies**. The model reuses saved date/time anchors when unconstrained and adapts only missing fields when an anchor conflicts with the source setting. Contextual values returned by the model take precedence. If a required field is still `Unknown`, omitted, or preserved without a starting value, the backend fills it from the saved safety default without another model call. The safety defaults are deliberately generic; contextual scene fitting depends on the extraction model.

Every character profile has separate **age** and **gender** text fields. The tracker extracts established values from factual card definitions, the selected opening and applicable lore. Age can be an exact age, a range or description such as **Early thirties**, **Adult; exact age unknown**, **Ageless**, or **Ancient; appears to be a young adult**. Gender preserves the source wording without a fixed list. Missing values remain `Unknown`; these fields are never invented by scene defaults or guessed from names, appearance, clothing, species, occupation, stereotypes or pronouns alone. Routine tracking preserves them until an explicit correction or supported canonical change. New `identity` summaries focus on species, occupation, origin, titles and social identity; older identity prose is preserved.

Known age/gender appear in the drawer and the readable roleplay/image snapshot as `AGE` and `GENDER`. ImageGen should use a source-established apparent age when it differs from chronological age, preserving uncertainty. Unknown values are omitted from the readable text, and the rest of the private profile remains excluded from image context. Existing chats can use **Fill Missing Age / Gender** to extract only unknown values from their saved card sources without rebuilding scenes or replaying turns. It fills the same still-missing fields in the baseline, current state, original setup and checkpoints, preserving existing values, other fields and provenance. If the sources do not establish the information, it stays `Unknown`.

Missing **outfits for model-controlled characters** are also automatic, independent of the checkbox. When clothing is entirely unspecified, the model chooses a simple outfit compatible with the setting, weather and established preferences. Existing clothing, including partial descriptions, is preserved without adding layers, accessories, possessions or physical traits. Explicit absence of clothing is preserved, and characters for whom clothing is inapplicable receive an explicit clothing condition. The user's outfit is never generated.

**Fill missing scene details** is an optional checkbox beneath Create and in the drawer. It starts off and applies only to that setup. Enabling it permits minor grooming and mild mood for model-controlled characters when those fields are missing, plus a brief sensory atmosphere in the world context beyond the automatic starting weather. Existing grooming facts stay intact; grooming cannot invent physical traits. The option does not authorize user-character details, history, relationships, consent, health, plans or events.

The backend saves its world defaults before the first extraction call and reuses them during repair, explicit Retry Setup and worker restarts for the same sources. Successful setup saves chosen details as starting continuity. Reopening, reprocessing turns, exporting/importing and inheriting a fork reuse them without another setup call. Outfits change only through supported story events. Existing chats and imported setups are not backfilled, even if their clock, weather or outfits are unknown. Changing the selected opening or explicitly rebuilding native card profiles creates a new baseline and may choose new defaults. Routine tracking and imported-profile refresh retain their factual recording rules. Filling adds no generation stage; malformed output still has the existing single repair limit.

An uninitialized chat displays two matching purple setup buttons beneath its opening message, each centered above a short description: **Import Saved Setup** loads saved profiles and a starting scene; **Create From Character Card** builds profiles and a scene from the card. These are temporary interface controls: no hidden placeholder message is created. The engine waits for this choice before making an extraction call. Canceling import leaves both choices available. The drawer offers the same actions if the opening is scrolled out of view, no opening message exists, or inline controls are unavailable. Import remains limited to chats with no user turns and no already-loaded setup; an uninitialized chat with existing user turns can still choose Create to track its history.

After choosing Create, the chat controls and drawer show the actual stage: reading cards/lore, generating profiles, validating, repairing rejected output if needed, and saving. Elapsed time updates locally once per second without polling or extra generation calls. There is no estimated completion percentage. A finished setup retains its completion time in the drawer; the temporary chat controls retire and the original opening remains.

If setup fails, its last stage, elapsed time and bounded diagnostic remain saved in the drawer, where **Show error details** expands the diagnostic. The chat's inline controls show a green **Character profile created. Complete setup in Story Continuity.** bar when validated profiles are available, or a neutral **Setup paused** message when none were extracted. Failure stages, stopped timing and diagnostics are not shown inline. The icon retains its red attention marker, and Create becomes **Retry Setup**. Status checks, reopening the drawer, background events, settings changes and worker restarts do not retry a failed initialization. Select Retry Setup explicitly; it uses the current checkbox choice and sources. Interrupted runs retain their last stage and show time to the last saved update in the drawer. Older failures without timing show that elapsed time is unavailable. A failure during saving can retry with an already valid baseline without generating profiles again. Import can still replace a failed setup locally in a fresh chat.

An incomplete setup can still show its validated character profiles, places and available scene fields in the drawer. The snapshot is labeled **Setup incomplete**; invalid world fields say **Unavailable — needs repair**. Private profile details require the existing private-state checkbox. This preview survives reopening/restarts, but does not enter story prompts, variable mirrors or setup exports until the whole setup succeeds. Existing valid checkpoints remain visible during ordinary tracking failures. Complete cached response excerpts from older failed setups can recover a preview locally; truncated excerpts cannot reconstruct missing profiles and require Retry Setup.

No setup, progress, error or completion message is added to the transcript for these controls. Legacy placeholder/completion notices are removed on the next enabled reconciliation, including before setup has been chosen. The imported setup's separate metadata anchor is retained for recovery. Previously initialized chats resume without a new choice or extraction solely from upgrading. Waiting for setup persists across reopens and worker restarts; sending a normal turn does not silently choose creation.

Interface controls never enter story tracking, branch fingerprints, recall or outgoing roleplay prompts. Legacy notices remain excluded, and deleted notice IDs stay filtered from already assembled prompts during that worker's lifetime. Removing the controls does not change the opening or saved continuity. A failed legacy notice deletion is retried on a later reconciliation.

After each eligible completed assistant turn, the engine supplies the extracted stable profiles inside the relevant previous state, a compact identity catalog, and that interaction to the tracker. Original cards are sent in full during initialization and explicit profile refresh. Routine updates consult the frozen sources locally and include only relevant reference excerpts for facts missing from the extracted profiles. Guidance, example dialogue and the original opening are excluded from factual lookup excerpts. Current story changes take precedence over starting conditions.

Tracker responses use compact changes such as `{id:"c1",action:"update",changes:[{field:"visible.dressAndLayers",value:"Coat folded on bench"}]}`. Unchanged fields and omitted entities retain their saved facts. Initialization still extracts all supported facts and applies the same starting-scene defaults. New NPC/user declarations can supply only their name and established facts; the backend fills unsupported fields with `Unknown` and assigns the correct role/controller. Relationships must reference existing characters or explicitly declared new characters. Creation slots are not established identities.

Preserved records restore their saved contents before copied replacement fields are validated. Validation lists invalid references together, with record indexes and offending aliases. One targeted repair can replace rejected records and add their missing declarations while valid candidates remain in memory. A field-specific repair retains unaffected changes inside the same record, including initial date/time/weather during a scene-status repair. Every rejected field must be corrected explicitly; returning empty arrays leaves that component unresolved.

If repair still fails, the backend saves independently valid changes and keeps each rejected field at its previous value (or Unknown for an otherwise valid new record). For example, invalid relationship `privateState` no longer discards a valid profile, outfit, time or public relationship update. As a last resort, otherwise valid overlong `relationships.privateState` and `world.immediateContext` prose can be shortened to fit 1,600 characters, preferring a sentence or word boundary. The drawer explicitly marks these fields **shortened** with their original length; shortening can lose trailing details, so the warning remains until a complete valid replacement is supplied. Reserved markup is never accepted by shortening. Identity, clock, boundary, objective and physical fields keep their existing rejection/dependency safeguards. Invalid identities/references hold the affected record and its dependents. Invalid physical changes hold proposed visible character changes, location/contact and place state together to avoid half-applied transfers or movement; invalid clock changes hold proposed date/time together. The retained result must still pass complete validation and the selected-branch check. Unreadable responses with no usable candidate, unsupported response formats and failures that cannot be safely localized still retain the prior checkpoint.

The drawer shows **Partial**, identifies affected fields with character/place names, and lets later turns continue from the accepted state. Repeated failures for the same canonical entity and field appear once. A later complete valid replacement automatically clears that field's current warning, including an explicit replacement equal to its old value. Omission, preserve, another field, and another relationship do not clear it. Relevant pending fields are flagged in the next ordinary tracker request without expanding entity selection or inventing missing history. Historical failure metadata stays attached to its checkpoint: rewinding or forking before the correction restores that branch's warning, while reopening the corrected branch stays clear. Older checkpoints can resolve warnings through recorded value changes without migration or replay. **Retry Incomplete Tracking** corrects the earliest checkpoint still contributing an active warning using its original turn, permits only unresolved changes, and then replays later turns where needed. Accepted values cannot be reapplied by that correction. Reprocess still reruns a whole turn.

Relationship `publicStatus` describes the publicly established dynamic. `privateState` summarizes current supported private trust, closeness, guardedness, feelings, tension and still-active obligations, respecting direction and user control. The tracker is instructed to use a few short sentences, usually around 200–500 characters when needed, and to consolidate existing recaps faithfully when selected. Relationship-specific limits and concerns belong in `boundaryOrConcern`. Completed events are retained through their lasting consequences rather than repeatedly appended as a chronology. `world.immediateContext` likewise summarizes the present scene and pending immediate actions. All descriptive fields retain the 1,600-character hard limit; names allow 160 and supplied IDs/references 180. Both the tracker and its repair receive these limits, and validation identifies the actual length/maximum, empty text or reserved markup precisely. Semantic summarization remains a model responsibility; the backend only validates and, for the two summary fields above, applies the warned fallback.

Compact schemas constrain both field names and controlled values: scene status is `active` or `ended`; objective status is `active`, `completed` or `abandoned`. These choices also appear in instructions and validation diagnostics. Casing/whitespace normalize locally. An `Unknown` scene-status value retains the existing status, or the initialization default of `active`, rather than inventing a transition.

During native initialization, programmatic date/time/weather defaults apply before validation, so unresolved values alone do not consume a repair or block setup. Invalid exact dates/times, missing model-character outfits and record/reference errors still use the single repair. The repair retains already extracted profiles, appearance, scene facts, saved world defaults and cast order. The initialization checklist makes starting outfits and the backend fallback explicit even with optional scene details off. Required card characters, starting conditions and model-character outfits must validate before setup becomes ready; otherwise the incomplete preview and **Retry Setup** remain. Optional failures such as invalid relationship prose can save a complete baseline with a Partial warning. Routine tracking and imported-profile refresh do not gain permission to invent missing scene facts. Full card-profile refresh retains its existing validation behavior.

The drawer shows the last tracked message, the effective output mode from the latest tracker request, partial-save warnings, and whether it is displaying a saved failure with automatic retries paused. Under **Private tracker state**, enable **Show Private Tracker State** and expand **Tracker diagnostics and response excerpt** to inspect both attempts, provider/model, finish reason, response size, tool-call count, errors, and a bounded rejected-response excerpt. Totals count first-pass successes, repaired successes, partial saves, failures, elapsed milliseconds and output tokens. These private records stay outside narrative prompts, variable mirrors and exported setups. Initialization progress remains available separately. Turning private inspection off or changing chats clears the displayed evidence.

Relevance selection retains the focused main character, user character, mentioned or colocated characters, current/mentioned places, relationships between selected characters, and immediate objectives. Scoped tracker results merge into complete canonical storage; omitted entities persist and cannot be overwritten by an out-of-scope update. The backend validates the result and branch fingerprint before committing a checkpoint. Routine rechecks do not make model calls or change revision timestamps.

Place selection also checks selected characters' recorded positions. When the scene uses a sublocation such as “Platform,” it retrieves the saved place only if that wording matches one place's name/description; ambiguous descriptions retain uncertainty. Connections alone do not establish the current place. The identity catalog marks each existing alias with `canUpdate`; reference-only entities remain available for identity lookup and character references, while provider schemas limit output records to selected entities and new creation aliases.

All extension-generated model context uses short entity aliases: `c1` for a card character, `n1` for an NPC, `u1` for the user, `p1` for a place, `r1` for a relationship, `o1` for an objective, and `l1` for a source lore entry. Names accompany character/place aliases. The backend maps these aliases to the original persistent IDs; the model never has to copy GUIDs. The same mapping is derived from the full saved cast for each request, even when only selected entities are sent. Use names in story prose; aliases are internal bookkeeping.

New entities use supplied creation placeholders such as `new_n1` or `new_p1`. The backend assigns their persistent IDs and resolves their relationship/objective references. Unknown, mistyped, duplicate, or incorrectly typed aliases and undeclared creation references receive one repair attempt. If unresolved, affected records and dependents retain prior values while independent valid changes can save. Aliases reduce copying errors but cannot guarantee that a model associates every valid alias with the correct facts. Canonical saves, chat-variable mirrors, setup exports, imports, and forks retain persistent IDs and require no migration for this release.

An unchanged existing record mislabeled `update` retains its saved facts and provenance, including outside the selected state. Changed out-of-scope records receive the single repair; unresolved changes are excluded from partial saves. If no safe partial result can be saved after repair, automatic retries of that unchanged rejected request pause across background events and worker restarts. The drawer retains the error and last valid checkpoint. **Reprocess Latest Turn**, an edit/swipe affecting the rejected turn's prefix, a tracker connection/mode/budget/timeout change, or refreshed source/state permits another attempt. Later turns wait behind these unrecoverable failures, while partial saves allow tracking to continue. Transient provider/network errors remain eligible for automatic retry when no candidate can be recovered.

Before the next roleplay prompt, the engine injects a selected private **labeled-text** snapshot capped at **24,000 text characters**. `CURRENT SCENE` contains the fictional clock, context, visible characters and places; private character context, relationships, commitments and private place facts are labeled separately. Names accompany short aliases. Context packing admits or omits whole saved field values without modifying storage. Current context, physical state, knowledge, boundaries and immediate commitments receive space before long profiles. The coverage notice explains that omission does not erase established facts. Lumiverse still supplies the normal character card, history, and other prompt sections separately. Canonical storage and tracker input/output remain JSON; rendering adds no generation call.

The drawer, injected `WHEN` line and visual macro show dates as **October 17 (Fall)** when that season is established, and exact times as **02:54 PM (Afternoon)**. Gregorian display dates omit the year; exact times use AM/PM and a short time-of-day label. Story-established descriptions are retained alongside exact values; a standalone **Fall** or **Late afternoon** remains valid when no exact date/time is known. Seasons are not guessed from months. The private tracker and existing JSON saves/macros retain calendar precision for calculations and rollovers. Rendering adds no model call or migration.

For image generation, use `{{getchatvar::story_continuity.visual_text_v1}}` in a Chat-aware Custom Main preset. It supplies labeled observable scene text with known **AGE/GENDER**, stable appearance, current hair/grooming, **DRESS & LAYERS**, positions and items. Other profile fields, secrets, internal state and objectives are excluded. Existing JSON macros retain their formats. See [image-generation parser instructions](IMGGEN.md), including the separate-parser freshness caveat.

Tracking macros:

| Macro | Contents |
|---|---|
| `{{getchatvar::story_continuity.state_v3}}` | Complete private schema-3 JSON, including profile age/gender. |
| `{{getchatvar::story_continuity.public_v2}}` | Observable JSON, with character-level age/gender and no other profile fields. |

Macros reflect the latest committed checkpoint and do not trigger extraction. Setup previews are never exposed.

|---|---|
| World | Fictional date/time, weather, location, immediate context, proximity/contact, scene lifecycle |

The user retains control over voluntary actions and internal state. User internal fields are normalized by rejection to `Unknown`; a result that invents them cannot be committed. NPCs and places persist when absent from a later output. Internally, established exact Gregorian dates use `YYYY-MM-DD`, and exact local times use 24-hour `HH:mm`; established relevant seconds are retained. Supported seasonal/time descriptions can follow in parentheses, such as `2031-10-17 (Fall)` and `14:54 (After lunch)`. Partial dates, fictional calendars and approximate times retain their uncertainty. Newly proposed unambiguous exact values normalize locally, while impossible exact dates/times use the existing single repair. Equivalent spellings preserve saved facts and provenance. The tracker is instructed to carry supported elapsed time across midnight, month and year boundaries and resolve supported deadline dates/times. Completed dialogue and action can imply a small, conservative advance without a stated duration. Brief gestures may leave the displayed minute unchanged; there is no fixed advance per reply, and an in-progress activity is not silently completed. Approximate clocks keep their uncertainty. Real waiting time and generation latency never advance the fictional clock. Existing/imported clocks are not backfilled or rewritten on load. `/look`, `/scene`, `/debrief`, and the imported setup's beginning recap do not produce tracker updates.

## Drawer and widget

The drawer uses Lumiverse native switches, selects, numeric inputs, checkbox, and badge when available; older hosts get themed HTML controls. Advanced and private sections use persistent details elements so mounted controls survive collapsing.

- **Tracking enabled**, **Show Widget**, tracker connection, output mode, output budget, timeout, **Save Settings**, and **Refresh Connections**.
- Startup **Import Saved Setup** / **Create From Character Card** choices beneath the opening message, with matching drawer actions and running setup stages/elapsed time. Failure details remain in the drawer; inline controls show the available profile or paused status and offer **Retry Setup**. While a file picker or setup request is pending, both actions are disabled to avoid duplicate choices.
- An observable snapshot of the world, characters/NPCs, public relationships, and recurring places.
- **Fill Missing Age / Gender** extracts only missing age/gender from saved card sources. It leaves known values, scenes, identity prose and other tracking intact. It does not reread newly edited card definitions; use Refresh Card Profiles for a deliberate full refresh.
- **Show Private Tracker State** explicitly reveals full state including profiles, secrets, knowledge, intentions, and objectives.
- **Reprocess Latest Turn** reruns the latest eligible turn against its preceding checkpoint.
- **Retry Incomplete Tracking** corrects unresolved components in the earliest partial checkpoint, preserving its accepted values before replaying later turns as needed.
- **Refresh Card Profiles** rebuilds a native baseline from the edited card and reconciles selected history. For an imported setup, it fills missing stable profile fields from that setup's saved sources while preserving its recorded scene and existing facts. Card edits are flagged before this action; opening edits/swipes rebuild native baselines automatically.
- **Clean Unused Tracking Files** scans only this extension's files, requires a second click to delete, and verifies candidates again. Malformed or unprovable files are retained.
- When **Show Widget** is enabled, the draggable, edge-snapping floating icon appears in an eligible chat as soon as its settings are available, including before a snapshot exists. It opens the drawer and reflects waiting for setup, generation, readiness or attention. It follows chat navigation, disappears on Home, respects reduced-motion preferences, and defers specialized cards to Date Simulator. Missing UI panels permission does not prevent tracking.
- The widget matches Image Browser's **48 × 48** footprint and **32 × 32** artwork. A purple/indigo/cyan book with a gold bookmark stays colorful in every state; its small indicator is amber for setup, cyan while processing, green when ready and rose with an exclamation mark for attention. Keyboard focus remains visible and reduced-motion settings disable the indicator pulse and hover transition.

“Private” means omitted from ordinary replies and the default snapshot. The model receives private state, the user can inspect it, and Lumiverse's prompt inspection can show the injected block. It is not encryption. The tracker is instructed to classify private facts correctly, but extraction accuracy still depends on the selected model.

## Original setup import/export

**Export Initial Setup** saves the original first eligible opening checkpoint, even after later play or reprocessing. It includes card sources and complete private initial state, with portable provenance. It does not include later checkpoints, chat IDs, or transcript history.

The secure-browser Save As API is used when available. Otherwise, **Download JSON File** appears. Canceling Save As writes nothing. Switching chats invalidates a pending export.

**Import Saved Setup** in the startup controls and **Import Setup — Choose File** in the drawer use the same picker and accept this extension's JSON format in a fresh generic chat with no user turns or generation in progress. No unused extraction call is needed before importing. An already-created greeting baseline does not prevent a later import while the chat is still fresh. Import validates the file before appending one neutral confirmation with private metadata. The metadata anchor can restore state after sidecar loss or a fork. **Begin Story** generates an observable opening through the host's normal generation API without a tracker call or fictional-clock advance. Editing, swiping away, or deleting the import anchor deactivates its state. Use a matching card for a reusable setup so its voice remains consistent.

## Compatibility and limits

- Date Simulator v1.4/v1.5 and Storyteller v1.6 cards/anchors are deferred to **Date Simulator Continuity Engine**, preventing overlapping generic injection. Their existing extension is unchanged. Its setup files are not accepted here.
- Initialization reads enabled **constant** lore entries attached to the cards when permitted. Conditional lore remains governed by Lumiverse activation; this release learns resulting facts from completed narrative rather than copying every conditional entry into state.
- State supports up to 24 characters total, 48 relationships, 32 places, and 12 objectives. Text fields allow 1,600 characters; total canonical state is capped at 64,000 characters. Original card/lore sources are capped at 96,000 characters. These are ceilings, not target lengths.
- Original-source retrieval uses local keywords and topic matching, capped at eight excerpts and 6,000 serialized characters per update. Long passages are marked partial. Matching is conservative and may miss a relevant detail; it does not make an extra LLM call to search. Use **Refresh Card Profiles** for deliberate re-extraction when needed.
- Tracker schema v2 adds explicit `profile.relationshipContext` and `profile.boundaries`, using Date Simulator's stable-profile coverage as a reference. Participant identity/disposition/preferences/relationship/boundary facts are generic per-character fields; initial context stays in the world/character baseline. Date Simulator is not a runtime dependency.
- Saved schema-v1/v2 state and portable setups upgrade locally to schema 3 without a model call, history replay or provenance change. Missing age/gender start as `Unknown`; legacy identity prose is not parsed or rewritten on load. **Fill Missing Age / Gender** can backfill them from saved sources. The complete mirror is `story_continuity.state_v3`. Existing `state_v2`, `state_v1` and `public_v1` keep their prior JSON shapes; age/gender are omitted from those compatibility projections. The new `public_v2` includes only age/gender from the profile alongside observable state. The selected readable `visual_text_v1` adds known `AGE`/`GENDER` labels.
- Tracker output supports 400–32,768 tokens (default 16,384). Timeout supports 5–300 seconds (default 300). Existing saved settings retain their chosen values; change them in the drawer and select **Save Settings** to use the new defaults in an existing installation. Original output and its one repair share a deadline, capped by the remaining 300-second reconciliation budget. Large existing chats can require another reprocess pass after that budget; completed checkpoints are retained.
- **Auto**, **OpenAI-compatible JSON Schema**, **OpenAI Responses JSON Schema**, **Anthropic Tool**, **Google JSON Schema**, and **Plain JSON (prompt only)** are selectable. Auto selects a structured mode for recognized providers; other providers use prompt-only JSON. Quiet tracker requests clear narrative stop sequences and pin a resolved default connection. OpenAI mode uses Responses formatting when the selected preset requests it and is readable, otherwise Chat Completions formatting. Explicit Responses mode works without the additional host Presets permission. The drawer records the effective mode. Schemas enumerate entity aliases and permitted field paths; strict local validation owns cross-record dependencies, field bounds, role protection and provenance.
- The engine records continuity. It does not autonomously simulate off-screen actions, forecast real weather, invent missing history, or replace the host's character definition.

## Development and validation

```sh
npm ci
npm run check
npm run package
```

`npm run check` builds both entries, runs schema/alias/state/context/tracker/backend/DOM tests, and validates the package. Tests cover message-free setup choices, initialization stages/timing and explicit retries, legacy notice cleanup/filtering, GUID-free context, identity allocation and repair, cross-references, provider formats, routine context selection/budgets, v1 migration, privacy/user control, branch edits and stale results, forks, import recovery, frozen exports, navigation, cleanup confirmation, and native/fallback drawer controls. Provider transport and lifecycle paths are checked separately rather than repeating their full Cartesian product. Package validation starts the built backend and verifies the frontend's `setup` export instead of searching for internal function names. Legacy notice and v1 migration tests remain because existing chats and setup files can still contain those formats.

`npm run smoke` explains the opt-in live provider suite without making requests. To run it, set `LUMIVERSE_URL` to your local server, `STORY_SMOKE_CONNECTION` to an existing connection ID, and `LUMIVERSE_COOKIE` if your server requires session authentication; then use `npm run smoke -- --live`. Optional `STORY_SMOKE_OUTPUT_MODE` overrides Auto. The suite exercises initial extraction, clothing changes and a new NPC through Lumiverse's real quiet-generation endpoint, using synthetic fixtures and up to six generations. It creates no chats or saved story state and prints only outcome/usage/timing metadata. Live results are separate from deterministic unit-test coverage.

For a standalone visual preview, serve this directory locally and open `test/browser-preview.html`. It uses the actual frontend with fixture data and simulated setup transitions, including an import-picker cancellation. It does not access Lumiverse or make model calls. Startup controls, the pre-generation widget and the drawer have been inspected in dark and light themes. Live provider behavior and an installed Lumiverse session still require an integration run.
