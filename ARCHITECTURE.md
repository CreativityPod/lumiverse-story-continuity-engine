# Architecture

`schemas.js` defines canonical state, strict local validation, backend-owned provenance, public/private projections, v1/v2 upgrade and source remapping. `protocol.js` defines the compact change-record schema, deterministic expansion and structured validation errors. `clock.js` normalizes exact tracker clock proposals and creates/applies initialization world defaults. `aliases.js` maps persistent identities to per-request aliases, enumerates provider ID choices, validates model references and allocates new persistent IDs. `partial.js` recovers independently valid changes and limits retries to unresolved components. `retrieval.js` optionally supplements deterministic relevance through the Decision API; `context.js` selects relevant entities, packs bounded roleplay/visual context, and searches frozen sources locally. `render.js` deterministically renders labeled story and observable-only image text. `diagnostics.js` bounds private attempt evidence. `state.js` handles storage normalization, sources, branch fingerprints, portable setups and prompt injection. `tracker.js` performs provider-aware quiet generation and targeted repair. `backend.js` owns storage, queues, reconciliation, import/export, fork inheritance, scoped status, mirrors, and cleanup. `frontend.js` owns the drawer and widget.

The implementation uses the existing Date Simulator engine's architecture and host API patterns, with an independent generic schema and lifecycle. No runtime imports reach into that extension, and its source files remain unchanged.

## Initialization and source changes

A card-read pass loads chat membership, card definitions, the selected opening, and permitted attached constant lore. Stored card identities use `char:<host-card-id>`; new recurring NPCs, places, relationships and objectives receive backend-generated UUIDs with `npc:`, `place:`, `rel:` and `objective:` prefixes. The user uses `user`. Existing imported identities remain unchanged. Raw sources and their fingerprint are stored separately from the extracted baseline. Every card must have a corresponding main-character entity. Unsupported fields stay unknown except for authorized starting scene defaults. Card changes are surfaced for an explicit profile refresh; selected-opening changes automatically invalidate the baseline because that scene seed is no longer canonical.

Native initialization appends an explicit scene-default policy to the same extraction request. The model extracts source-established world date/time/weather, including partial/approximate values, fictional calendars and explicit absence of ordinary weather. Before generation, the backend saves optional envelope metadata `initialWorldDefaults: {sourceFingerprint, values: {date, time, weather}}`. Random defaults use 2020–2039 Gregorian dates, any minute of a 24-hour day and a small modest-weather pool, independent of the wall clock. The request includes those choices as saved anchors and last-resort safety values. The initialization-only policy first extracts established facts, then authorizes the model to choose wholly missing fields together as a coherent scene, fitting source era/calendar, location/climate, season, opening activity and time of day. Partial fields and brief weather descriptions remain established and are not embellished. Unconstrained date/time reuse the saved anchors; incompatible anchors may be adapted only for missing fields. Missing weather gets concise contextual conditions, optional approximate temperature when the setting supports it, and indoor/non-weather-world handling. Unsupported geography, daylight, seasons, forecasts, future events and unrelated scene facts are excluded. Contextual fitting is a model responsibility; the programmatic backstop remains generic. After compact expansion and before world validation, `decodeModelOutput` fills only `Unknown` date/time/weather from the saved choices; omission or preserve expands to the same unknown scaffold when no prior value exists. Extracted known values take precedence. Invalid types or impossible exact clocks retain the normal validation/repair path. The choices persist across both attempts, explicit retry and restarts for the same sources. Store normalization drops corrupt or different-source defaults without changing committed state.

Model-controlled characters must also have `visible.dressAndLayers`: preserve source clothing, including partial descriptions or explicit absence, otherwise choose a simple compatible outfit or record that clothing does not apply. User-controlled clothing may remain unknown. Local validation collects unknown required outfits with other errors through the existing single repair path. The per-setup `fillMissingSceneDetails` boolean defaults false, travels with `story_create_setup`, persists in the existing envelope and appears in status for retry/reopen UI recovery. When true, the policy additionally permits missing model-character grooming/mild mood and sensory atmosphere in `world.immediateContext`; outfit and world defaults apply independently. These are prompt-level semantic restrictions; canonical user-internal validation remains enforced locally. No extra model request, provider format, canonical field or portable migration is added. Routine updates and imported-profile refresh never receive the policy, programmatic defaults or the extra starting-value validation. Committed defaults persist through checkpoint replay, forks and portable exports/imports; the private fallback metadata itself is not exported. Source/opening invalidation intentionally creates a new baseline; existing/imported baselines are never backfilled simply on upgrade.

The ordinary greeting is initialized once, then receives a checkpoint without being processed as a second event. Later selected assistant turns receive scoped state updates: world plus relevant existing entities and new directly established entities. Model outputs cannot supply canonical message IDs: `preserve` copies prior data and provenance; `update` receives the current assistant ID in backend code. Exact unchanged entities retain their previous sources even if the provider labels them updated. Omitted entities remain persistent, and out-of-scope existing entities cannot be updated. Controller roles cannot change, and user internal fields must stay unknown.

## Temporary setup panel

Optional envelope field `setupProgress` stores the current initialization stage, running/failed/ready status, wall-clock start/update/finish times, original/repair attempt, bounded diagnostic and interruption marker. It never enters canonical state, portable exports or model prompts. Tracker callbacks report generation, validation and the single repair; reconciliation reports source reading and saving/ready, persisting and publishing each transition. Stage reporting adds no model requests. The frontend shows running stages in the inline group and drawer, measures elapsed time from the latest server duration plus local time, and owns one local timer that stops on failure, completion, navigation and unload. Failure stages, stopped timing and the expandable diagnostic are drawer-only; that disclosure preserves its open state across status refreshes. Inline failure presentation uses a green profile-created bar only when `setupPreview.snapshot.characters` contains validated records, with a reminder to complete setup in the drawer. Without a profile it uses a neutral paused bar, including older failures without progress metadata. Inline error text is cleared, not merely hidden. The icon and backend failure state remain unchanged; Retry remains explicit. Starting a retry restores normal running progress and elapsed time.

Optional `setupDraft` is a display-only preview keyed to the frozen source fingerprint. Failed decoding attaches independently validated entity records and world fields; dangling references and rejected records are excluded. A canonical-shaped scaffold validates its internal integrity, while `unavailableFields` masks fallback world values as unavailable in both public/private drawer views. It is never selected as `current`, a baseline or checkpoint, and cannot enter mirrors, exports or injection. Private facts use the existing opt-in inspection path. The preview persists before repair, survives failed/interrupted attempts and retires on success. Normalization rejects corrupt/different-source drafts without discarding committed state. When no draft exists, a complete cached initialization response can rebuild one locally; bounded/truncated evidence is never treated as a complete response.

Failed initialization is gated before source extraction and generation, including background events, status checks, configuration changes and worker restarts. Only the explicit Create/Retry action passes `retrySetup`, clears the previous failure and starts a new run. Legacy initialization failures acquire a generic setup stage without invented timing; stored running operations after worker interruption become inspectable failures with time to their last saved update. Native opening/source resets carry an active run but do not release an existing failure. A valid import bypasses the native failure gate and clears initialization progress. If baseline saving/mirroring fails after a valid baseline exists, Retry can finish saving that baseline without generating it again. Successful baseline generation is marked ready before history catch-up, so a later routine-turn failure does not mislabel profile creation as failed. Routine rejection memoization and transient-error behavior remain separate.

Before first-time baseline extraction, the backend waits for an explicit Import/Create selection without adding a chat message. Optional envelope fields `initializationMode` and `awaitingSetup` persist the user's Create decision and waiting state. `setupTargetMessageId` identifies the first narrative assistant opening (or first narrative user message when no assistant exists); it is only a DOM target. A chat with no target uses drawer controls. The target clears once a valid baseline is saved or imported. Existing baselines/revisions imply previous authorization during normalization. Canonical schema 2 and portable format 1 remain unchanged.

`story_create_setup` validates the user's choice and runs its extraction attempt in one serialized queue operation, preventing a queued status/event from starting an extra attempt between them. No message event, status refresh or interceptor implicitly chooses creation for an uninitialized chat. Import retains its separate validated metadata anchor and restores locally without an extraction call. The frontend receives `canCreate`, `canImport`, `awaitingSetup` and `setupTargetMessageId`, then attaches extension-owned controls directly beneath the narrative opening via `ctx.dom.inject`. Both buttons use the same primary styling and are centered above short descriptions. The optional scene-details checkbox beneath Create stays synchronized with the drawer, preserves an unsent choice across status updates and resets on chat navigation. It is disabled during pending work and retires with setup controls. Running progress appears in both locations; failure details stay in the drawer. Render events handle an opening initially outside the virtualizer viewport; the host preserves controls/listeners across remounts. `uninject` retires only that group after readiness or navigation, leaving the original story content intact. Drawer controls remain available without an opening or inline support. Both entry points preserve file-picker user activation, prevent duplicate actions while pending, and discard picker/results from an old chat. Begin Story uses the supported `triggerGeneration` append option.

Enabled reconciliation removes legacy choice, generating, failed and ready setup notices, even while awaiting the user's setup choice. Cleanup targets extension-marked initialization rows and excludes the import recovery anchor. It does not generate profiles, change revisions or rewrite checkpoints. Legacy envelope fields `setupNoticeId`/`setupNoticeShown` remain compatible but no longer anchor the interface. Failed/canceled file selection leaves the controls available.

Legacy notices remain excluded from greeting selection, eligible assistant turns, user-turn association, specialized-card marker detection and prefix fingerprints. Their edits/deletion therefore do not invalidate checkpoints or become narrative events. Branch matching resolves the target story message by identity before comparing narrative prefixes. Canonical state and fork provenance continue to use only actual tracked turns.

The roleplay interceptor strips legacy notice rows by extension metadata or host source-message identity, including when tracking has failed or is disabled. A worker-local ID registry also filters deleted notices from prompts assembled before cleanup. Fixed-text matching retains legacy choice/ready text support and preserves user-authored text. Message event handlers ignore managed notice deletions so cleanup cannot queue recursive initialization or retries. New controls never enter the transcript, recall or outgoing prompts.

Legacy cleanup is best effort and never gates an authorized Create/import operation. It rereads the transcript and never recreates a notice. A failed deletion retries on a later enabled reconciliation. Once a profile exists, later history-tracking failures stay in the drawer and do not retain the setup controls. The envelope remains version 1 with backward-compatible optional startup fields.

The floating widget is gated by active chat, widget preference and specialized-card routing rather than snapshot presence. Its first status can therefore render the icon before extraction. Subsequent chat navigation uses the known preference while loading that chat's status. Waiting, processing, ready and attention states update the same widget; Home, preference-off, chat changes and unload clean up the previous instance. Late status responses from another chat cannot change its state.

The chat widget uses the same 48 × 48 chromeless host dimensions and 32 × 32 SVG dimensions as Image Browser. Its full-size button contains a separate filled, gradient book SVG; the drawer retains its existing line icon. An extension-scoped SVG gradient ID avoids collisions with other extensions. A small status badge supplies state color without recoloring the artwork; only the processing badge pulses. Hover and keyboard focus follow the reference widget's interaction treatment, with reduced-motion overrides. This adds no runtime dependency on Image Browser or external image assets.

## Model identity protocol

The backend derives a typed alias registry from source-card order and the complete canonical collections before selection. Card characters use `c1`, NPCs `n1`, user characters `u1`, places `p1`, relationships `r1`, objectives `o1`, and lore sources `l1` (subsequent identities increment each prefix). Selecting or focusing a different actor does not renumber the registry. The registry is local to the request and rebuilt for future requests; no model-supplied alias map is trusted or persisted.

Initialization sends aliased card/lore definitions. Routine tracking sends aliased selected state, references and the complete identity catalog. Imported profile refresh supplies aliased sources and baseline. Roleplay injection also encodes aliases before packing its JSON budget. Source message IDs and irrelevant raw card metadata are excluded, and known persistent entity IDs embedded in supplied text are replaced. The host's original card/history and explicit user-authored prompt templates remain under Lumiverse's control.

The catalog reserves every main-character alias before initialization and offers separate `new_n1`, `new_u1`, `new_p1`, `new_r1` and `new_o1` creation slots within collection limits. A creation slot does not establish an identity. New NPC/user records require a name and `action:update`; unsupported fields default locally to Unknown and roles/controllers come from the slot. Main-character creation is never offered. Catalog entries mark existing identities with `canUpdate`. Provider schemas enumerate selected/creation IDs and valid change field paths. Reference values are checked against the full registry and declarations after decoding. Reference-only identities stay available for cross-references but must be omitted as output records. A full, unselected collection uses `maxItems:0` with a nonempty typed ID enum.

The wire shape uses `{id,action,changes:[{field,value}]}` for entities and `{action,changes}` for world. All root collections remain required. Omitted changes inherit saved fields; omitted entities persist. Initialization must still include every card and all supported extracted facts. Legacy full responses and sparse plain-mode records expand through the same validator. Unknown fields, duplicate changes, invalid IDs, role/controller mismatches and dangling references remain errors. Preserve restores a saved record before interpreting replacement fields; explicit identity-role contradictions remain rejected.

Change items use nested schema alternatives to bind enum-valued fields to their canonical choices; the unconstrained text branch excludes those fields. The same choices appear in prompts and indexed errors. Enum casing/whitespace normalize, and Unknown scene status retains the prior/default active status. For a field-specific error, repair replaces the rejected field while retaining other proposed fields within that record, including legacy full-record values. Invalid patch value types and duplicate known fields also identify their exact field. Omitted corrections remain unresolved for partial recovery. Contract upgrades release old routine rejection signatures without replaying valid checkpoints.

Decoding collects indexed record/reference issues and allocates stable UUIDs for declared new entities, reusing allocations across repair. Native initialization fills unresolved date/time/weather from the saved programmatic defaults before world validation. Missing model-character outfits still join record/reference issues before any repair, so a reference-only correction cannot exhaust the repair allowance before an outfit omission is reported. Missing-outfit issues carry exact field paths and aliases; structurally valid profiles remain available in an incomplete preview. Invalid world fields retain their unavailable markers. When every issue identifies a known record, the repair returns replacements for all rejected records and required new declarations. Valid candidates remain frozen in memory; an omitted rejected record or required correction remains unresolved. Replacements retain the original collection order, and newly declared entities append, avoiding alias renumbering from repair alone. Existing valid creation declarations remain part of that combined candidate. Unparseable responses, unknown identity errors and scope errors request a complete replacement. Every accepted result, including partial recovery, is revalidated for references, scope, provenance and branch identity before committing one valid snapshot. Character/place aliases in prose become names. Alias validation cannot detect every semantic misassignment to another valid alias; extraction accuracy still depends on the model.

After unsuccessful repair, partial recovery removes invalid field proposals from a usable schema-3 candidate, allowing prior values (or new-record Unknown defaults) to inherit. Valid corrections from an incomplete targeted repair merge with the original candidate first. Identity/reference failures hold whole affected records; decoding then discovers and holds dependents whose declarations are missing. Invalid physical fields or character identity/scope failures hold all proposed character visible fields, world location/contact and place currentState together. Invalid date/time holds both proposed clock fields. Objectives are held as complete records on any failure. Recovery repeatedly decodes/materializes the retained result; unlocalized errors, invalid root formats, required card omissions and incomplete initial conditions/outfits remain hard failures. No new provider request is added, and full profile refresh keeps its prior behavior.

The tracker contract defines relationship privateState as current qualitative relationship dynamics, publicStatus as publicly established dynamics, and boundaryOrConcern as relationship-specific limits/concerns. Summarization preserves asymmetry, user control, active obligations and uncertainty while consolidating obsolete chronology. Selected existing recaps may receive a faithful wording correction. world.immediateContext stays focused on present circumstances and pending immediate actions. Shared TRACKER_TEXT_LIMITS supplies the unchanged local limits and provider-visible instructions. Validation retains code invalid_text while distinguishing empty text, actual/maximum length and reserved markup; the normal single repair receives explicit summarization guidance. Provider schema shapes remain compatible.

If that repair fails, otherwise valid overlong privateState/immediateContext can use bounded local shortening at a sentence/word boundary, avoiding split surrogate pairs. Reserved markup anywhere in the original value disables this fallback. Other fields retain their prior validation behavior. A truncated_text issue records the original length, and the full retained state still passes scope/reference/provenance checks. The shortened summary is saved and visibly marked incomplete; local shortening is not semantic summarization and can lose trailing details. Shortened values do not issue complete-replacement receipts.

Optional `baselinePartial` and checkpoint `partial` metadata contain bounded unresolved paths, field masks and canonical identities. Rejected prose stays in private diagnostics. Public status supplies bounded component paths/source message IDs and a Partial warning, with no private field values. Partial checkpoints participate in normal branch reuse, mirroring and later-turn tracking. The metadata survives restart and valid fork inheritance with remapped source message IDs; it is excluded from canonical schemas, macros, narrative injection and portable exports. Partial outcomes have a separate metric.

Optional checkpoint acceptedUpdates receipts store only canonical identities and explicitly accepted field paths. They distinguish a valid same-value replacement from omission/preserve, and exclude failed, shortened and unselected no-op proposals. activePartialUpdates derives current warnings in checkpoint order from those receipts and actual state differences, keying by canonical identity/field and retaining only the latest repeated failure. This also supports older checkpoints without mutating them. A different field/entity or an unidentified rejected declaration cannot falsely clear a warning. Rewinds/forks before a correction restore the relevant historical warning; corrected branches remain clear across restart. Public warning components use entity names and mark shortened summaries with original lengths, while historical evidence remains private. Relevant pending targets enter routine requests as bounded aliased guidance, filtered through the ordinary allowedUpdateIds; this adds no generation or reference-only updates.

The explicit Retry Incomplete Tracking action selects the baseline or earliest matching checkpoint still contributing a current warning, skipping historical failures resolved by later replacements. It corrects that historical checkpoint against its already accepted state and original sources/turn. Request aliases are rebuilt for that state. A local mask admits only its unresolved fields/records and necessary new character declarations, and keeps physical/clock groups coupled. Omitted corrections stay pending. Accepted fields cannot be applied again by the correction. A successful or partial correction merges its receipts into that checkpoint and invalidates descendants for ordinary replay; unreadable retry output leaves the checkpoint and warning intact. A complete optional baseline with invalid relationship prose can be committed as Partial, while required initial scene conditions still gate readiness.

The tracker classifies empty/malformed/wrong-type/reasoning-only responses, truncation, refusals, missing/ambiguous tools, semantic validation and transport failures. It preserves actual failed text/tool arguments for repair rather than substituting an empty object. Its original deadline covers at most two generations. Quiet requests override inherited stop sequences, pin the resolved connection, and select endpoint-appropriate schema parameters. Optional preset inspection respects Responses API selection; unreadable metadata falls back to Chat Completions. Auto fallback to prompt-only mode is explicit in diagnostics/UI.

Optional storage-envelope fields hold bounded private diagnostics, per-chat outcome/latency/token totals and the last tracked message ID. A diagnostic has at most two attempts, 64 indexed issues per attempt and 3,000 characters of response evidence per attempt. It contains no connection credentials. Public status carries mode/provider/model and bounded pending/retry metadata; excerpts require explicit private inspection and never enter prompts, mirrors or portable exports. The tracker contract revision is part of the rejection fingerprint so old failed requests can retry after upgrade without invalidating successful checkpoints. Failed initialization still requires explicit retry; transient transport failures retain existing retry semantics when recovery is unavailable.

Canonical schema 3, storage envelope 1 and portable format 1 stay unchanged for partial saves. Saves, mirrors, imports, exports and fork inheritance use persistent identities. No data migration or tracker replay is needed solely to adopt aliases or partial saves.

## Profiles and per-request context

Schema v2 adds `relationshipContext` and `boundaries` to each private profile. Date Simulator's stable CASE/MAN/WOMAN/DISPOSITION/PREFERENCES/RELATIONSHIP/CURRENT CONTEXT/BOUNDARIES/INITIAL STATE coverage guides extraction: identity, background, disposition and voice, preferences, relationship history/agreements, boundaries, private durable facts, and the separate initial scene baseline. No fixed woman/man roles or dating-specific response vector is imposed.

Initialization and explicit refresh see the full bounded sources. Routine tracking sees complete selected state records (including their extracted profiles), identity-only catalog entries, the completed interaction, and at most 6,000 characters of targeted source excerpts. Local keyword/topic matching ignores actor-name-only matches, already covered profile facts, unselected card owners, examples/creator guidance, and the original opening. Long source passages produce explicitly partial windows. Retrieval is heuristic; missing matches retain uncertainty rather than creating facts. Source data is treated as reference, and established narrative changes take precedence over baseline descriptions.

Place selection includes names/IDs in the scene and selected characters' positions. When a location has no direct named match, its non-prepositional words must all match one saved place's name/description before that place is included. Numeric qualifiers remain significant, ambiguous matches are omitted, and connections/private/current facts do not supply location evidence. Selection only retrieves committed records; it does not change presence or canonical facts.

An imported setup's explicit refresh extracts from its frozen sources with the imported baseline supplied. Backend code accepts only previously unknown stable profile fields from that result; existing profile facts, appearance, world/current state, relationships and objectives remain recorded. A changed profile baseline invalidates tracker checkpoints for replay, while the imported physical starting scene and anchor remain authoritative.

The roleplay projection uses the same entity selection but measures its 24,000-character budget against the rendered labeled text, reserving room for the longest omission notice. It preserves the focused actor, user, mentions, colocation, active relationships/objectives and current/mentioned places when relevant. Identities and current scene/physical facts take priority, followed by boundaries, knowledge/beliefs/intent, relationships and objectives, visible place facts, stable appearance, other internal state, profiles and private place facts. Each character-field priority runs across the selected cast before the next priority. Whole leaf values or records are omitted when they do not fit; context packing never modifies canonical storage. `render.js` separates observable CURRENT SCENE from PRIVATE CHARACTER CONTEXT, CURRENT ARC and PRIVATE PLACE CONTEXT. Omission notices preserve established facts rather than treating selection as erasure. The original host card/history remains separate, and arbitrary card prose is never deduplicated by guessing ownership.

The additional `story_continuity.visual_text_v1` mirror uses the same selector, alias registry, renderer and text budget in observable-only mode. The two source-established profile fields age/gender are explicitly whitelisted and rendered as AGE/GENDER; all other profile fields, internal state, private place facts, relationships and objectives never enter its packed projection. The budget is spent on visible state, current places and stable appearance. It is computed from committed state during ordinary mirroring, with no new model call. Existing full/public JSON mirrors and portable schemas remain unchanged. ImageGen reads the macro in its separate parser request; it does not wait for the roleplay interceptor, so immediate auto-generation can observe the preceding checkpoint. `IMGGEN.md` documents the supported labels and parser instructions.

Shared `formatStoryClockValue` presentation runs in the drawer and both labeled render modes. Exact Gregorian dates become month/day without a year, and exact times become 12-hour AM/PM with a clock-based period label unless a saved description is available. Source-established descriptions are preserved in the same date/time string using a trailing parenthetical; partial values and standalone seasons remain text. The formatter does not infer a season, hemisphere or actual daylight. `clock.js` is bundled into both entries so presentation stays consistent without runtime imports. JSON mirrors, canonical storage and portable setups retain their original precision; rendering does not mutate state or trigger generation.

Clock instructions require YYYY-MM-DD only for established complete Gregorian dates and local 24-hour HH:mm for exact times, retaining relevant established seconds. Exact tracker proposals normalize deterministically (including AM/PM, noon and midnight), retain a trailing parenthetical description, and receive range/leap-day validation with field-specific repair errors even when described. Approximate/partial/fictional-calendar values remain text. Omitted or preserved clocks and equivalent spellings retain saved facts/provenance, including imported baselines; loading never invents precision or migrates historical clocks. The tracker and roleplay injection explicitly allow conservative passage implied by completed dialogue/action, with no fixed tick per reply, added clock precision, completion of pending activities or unsupported time skips. Brief gestures can leave the displayed minute unchanged; observation/analysis and real waiting never advance time. Established weather persists until supported change. The model resolves narrated elapsed time, supported calendar rollovers and deadline timing; local validation checks representation and calendar validity, not the semantic correctness of the model's elapsed-time inference. Contract version 8 identifies schema-3 age/gender extraction without replaying valid checkpoints.

## Age and gender extraction

Both fields use the existing bounded string schema and compact paths profile.age/profile.gender. Exact ages, ranges, descriptive wording, chronological/apparent qualifiers and non-applicable conditions remain text. The tracker treats them as stable sourced identity facts, never random scene defaults or inferences from appearance, names, species, occupation or pronouns alone. New extraction keeps identity focused on other identity facts without rewriting legacy identity prose. New NPC/user declarations may omit them and retain Unknown. Provider schema/repair use version 3; existing persisted canonical states upgrade locally.

The explicit Fill Missing Age / Gender action runs in the per-chat queue. It requires a valid fully tracked selected branch, an unchanged opening/import anchor and no active generation. It supplies saved sources/current state to one ordinary profile-refresh request (with the usual single repair limit), without initialization scene defaults. Backend merging admits only source-extracted age/gender fields that were Unknown in the current character, and fills only still-Unknown copies in baseline/current/original setup/checkpoints. Other model changes, new entities and changes to known fields are ignored. Existing scene facts, identity prose, IDs, checkpoint fingerprints and source provenance are preserved; successful enrichment increments revision once. Unknown results do not change revision. Rechecks with both fields known require no generation. Message, source or selected-chat changes during extraction discard the result before saving. Imported and native setups share this scoped action; existing full Refresh Card Profiles behavior is unchanged.

## Jev-assisted context retrieval

Configuration adds `retrievalMode: "local" | "jev"` and `retrievalConnectionId`, defaulting to local and the empty default-Decision-connection selector. The optional manifest permission `decisions` is excluded from core required permissions. `decisionRetrievalAvailability()` checks the host `decisions-v1` capability, API and grant without requiring newer hosts for local tracking. The drawer lists Decision profiles through `api.decisions.listConnections({userId})`; the host remains responsible for profile ownership, credentials and protocol validation.

`retrieveRelevantState()` uses the complete canonical cast/relationship/place/objective collections as candidates, encoded through the existing alias registry without provenance or raw card/lore definitions. It submits one Score question per saved record (at most 116 under schema-3 limits) alongside the complete aliased saved state and the stage-specific exchange. Each question identifies its target alias in its instructions, since question keys are not model context. Instructions separate story evidence from instructions, relevance from presence/disclosure, and character knowledge from beliefs/suspicions and motivation. The backend accepts only complete, well-typed bounded Score answers with normalized probabilities. It never accepts proposed identities or values from this API.

The initial policy favors recall: include a saved record at score >= 0.5 on the 0-2 scale, or confidence < 0.5. `selectRelevantState(..., {retrievedIds})` unions admitted canonical IDs with the original local selection, validates IDs against saved collections, and closes dependencies for selected relationship endpoints and objective owners. Existing local priorities remain first during packing. This only broadens eligible context/update scope; tracking still requires supported changes, canonical validation, provenance and branch checks. Selection cannot itself change presence, transfer knowledge or convert a belief into a fact.

Before ordinary tracker generation, `runTracker()` retrieves against the completed exchange and uses the resulting context for aliases, permitted update IDs, references and pending-target filtering. Its Deadline starts before retrieval: Decision work is capped at five seconds and at one quarter of remaining time; generation and its single repair receive only the remainder. Setup/profile extraction, explicit partial correction and the targeted repair do not add a Decision call. The roleplay interceptor retrieves against the latest outgoing user input and previous stored assistant response after reconciliation. It rereads transcript fingerprints, revision/epoch, source/opening validity and config before injection; stale work is discarded. The visual projection explicitly ignores retrieved IDs and continues to run synchronously without private context or Decision calls.

Input exceeding 900,000 UTF-8 bytes is rejected locally without truncation, below the host's 1 MiB limit. A local abort plus Promise race bounds nonresponsive evaluations even when cancellation does not promptly settle. Invalid output, unavailable capability/grant/profile and transport/timeout failures retain deterministic selection. Decision output does not change canonical state. Successful selections are cached for 30 seconds in a per-API bounded eight-entry memory map; keys include full request, account, purpose, Decision connection and canonical identity mapping, preventing identically aliased chats from sharing the wrong IDs. Cache is cleared on settings changes, Decisions permission changes and deletion. No cache or raw relevance payload is persisted.

Retrieval diagnostics expose only mode/outcome, fixed explanations, model, elapsed time and total/selected/added counts. Tracking metadata is normalized with ordinary private tracker diagnostics and safely summarized in status; roleplay metadata is bounded worker memory. These metrics are separate from saved continuity and existing generation/token totals. This release does not implement secret access control, private NPC agents, reveal gates or simulation. It treats private state as character-specific knowledge and motivation, with beliefs/suspicions explicitly distinguished in prompt rendering. SCE's raw-source excerpt lookup remains heuristic.

## Transactions and branches

Each chat has an independent serialized queue and storage file under the extension's `chats/`. Safe filenames combine a normalized chat token with a fingerprint, avoiding collisions from normalization alone. A checkpoint records its selected assistant ID/swipe, complete prefix fingerprint, validated state, and commit time.

Reconciliation reuses only a contiguous checkpoint prefix. Edits, swipes, deletion, or invalid provenance cut reuse at the first unproven turn. The current state is reset to that prefix before another generation runs, so failed output cannot resurrect a discarded tail. Every generated result is checked against a reread of the selected transcript before commit. Initialization additionally rereads card/opening sources. Revision and revision timestamp change together only when a new baseline/checkpoint commits.

Fork inheritance reconstructs the copied source prefix from Lumiverse's `messageIdMap`, accepts only matching checkpoints, remaps all source IDs and checkpoint keys to the branch, and excludes later source turns. Missing or invalid maps trigger ordinary reconstruction instead of guessing. Imported baseline sources and frozen initial state are remapped too. A confirmed chat deletion immediately removes its exact-path tracking sidecar, clears per-chat selection/generation/notice references, and notifies affected frontends. If work was pending, another exact-path removal runs after its queue drains to catch an already-started storage write. A tombstone blocks later saves, tracking requests and stale selection/status requests. The frontend handles both the host deletion event and the backend notice to clear snapshots, private evidence, setup controls, exports and widgets without waiting for a navigation event. Existing orphan files remain eligible for explicit unused-file cleanup.

## Setups and authority

Portable format 1 is `{format:"story-continuity-initial-setup",version:1,sources,initialState}`. Every exported source ID uses `initial-setup`. File size, field shape, source card identities, canonical state, and source references are validated before import. The assistant anchor's neutral content, active swipe, and `metadata.story_continuity_setup` establish authority; its metadata is included in branch fingerprints. A valid import restores locally without tracker generation. Removing that anchor resets the imported epoch. Begin uses append-and-generate outside the continuity queue and is observation-only.

## Privacy, failure, and budgets

Canonical schema-3 state and the private `story_continuity.state_v3` mirror include separate text profile.age/profile.gender. Existing v1/v2 baselines, checkpoints and portable states upgrade conservatively during validation: age/gender initialize as Unknown, existing identity prose/facts/provenance survive, and migration makes no model call or revision increment. The storage envelope and portable format remain version 1; exported state uses schema 3. Compatibility state_v2 strips age/gender; state_v1 additionally strips relationshipContext/boundaries. The old public_v1 shape remains unchanged; public_v2 and the default drawer explicitly include only age/gender from the profile at character level. Other profile facts, internal state, private relationships, boundaries, objectives and source IDs remain excluded. Opt-in private inspection returns complete canonical state. Private facts are supplied selectively to the roleplay model with explicit knowledge and output boundaries. These boundaries are model guidance, not an encryption or access-control mechanism against the owner.

Structured output is checked for exact keys, leaf types, enums, bounds, duplicate identities, dangling references, unsafe managed markup, user-role changes, and provenance. Invalid output receives at most one repair, followed by local recovery of independently valid components. Failed components retain proven prior values and report attention; the two eligible summary fields may instead save a shortened value with attention. Unrecoverable responses retain the prior checkpoint. Tracker output defaults to 16,384 tokens and accepts 400–32,768; timeout defaults to 300 seconds and accepts 5–300. Existing saved settings retain their chosen values. Quiet original and repair requests share a timeout capped by the remaining 300-second reconciliation budget, matching the manifest's interceptor allowance. Long catch-up can resume from completed checkpoints. Tracker contract 11 releases old rejection pauses without replaying valid checkpoints; canonical schema 3, storage envelope 1 and portable format 1 are unchanged by summary recovery and warning resolution.

Exact unchanged records labeled `update` are safe no-ops even outside selection and retain provenance. All genuinely changed out-of-scope records are collected in a typed scope error before materialization; repair feedback names each alias and asks for their omission while keeping supported selected updates. Partial recovery also removes these records and their physical dependents. An unrecoverable final validation failure has code `TRACKER_STATE_REJECTED`. For routine turns only, the optional envelope field `rejectedTurn` stores a bounded diagnostic and a signature covering the contract revision, user, source/epoch, full prior state, turn prefix/focus and generation settings. Matching background retries return the proven checkpoint and diagnostic without generation, including after worker restart. Explicit reprocessing/profile refresh or a changed request releases the pause. Later turns remain behind an unrecoverable rejected prefix; partial saves let later turns continue. Provider/network exceptions are not memoized, and a usable earlier candidate may survive a failed repair request. This adds no canonical schema or portable setup migration.

Home navigation is explicit. Background events update their originating chat but cannot change the selected frontend route; late status/setup replies are ignored after navigation. Private display and prepared downloads are cleared on chat changes. Setup picker and native Save As calls begin inside user clicks. Cleanup confirmation is scoped to the requesting user and expires; candidates are rechecked inside their chat queue before deletion.
