# Architecture

`schemas.js` defines the provider action schema and canonical state, strict local validation, backend-owned provenance, public/private projections, v1 upgrade and compatibility projection, and source remapping. `aliases.js` maps persistent identities to per-request short aliases, enumerates provider ID choices, validates model references and allocates new persistent IDs. `context.js` selects relevant entities, packs the bounded roleplay projection, and searches frozen sources locally for targeted reference excerpts. `state.js` reads bounded source data, recognizes specialized cards, fingerprints selected message prefixes, finds eligible turns, validates portable setups and import anchors, and constructs prompt injection. `tracker.js` performs provider-aware quiet generation with a shared deadline and one repair. `backend.js` owns storage, per-chat queues, event reconciliation, import/export, fork inheritance, scoped frontend status, variable mirrors, and conservative cleanup. `frontend.js` owns the Spindle drawer and widget.

The implementation uses the existing Date Simulator engine's architecture and host API patterns, with an independent generic schema and lifecycle. No runtime imports reach into that extension, and its source files remain unchanged.

## Initialization and source changes

A card-read pass loads chat membership, card definitions, the selected opening, and permitted attached constant lore. Stored card identities use `char:<host-card-id>`; new recurring NPCs, places, relationships and objectives receive backend-generated UUIDs with `npc:`, `place:`, `rel:` and `objective:` prefixes. The user uses `user`. Existing imported identities remain unchanged. Raw sources and their fingerprint are stored separately from the extracted baseline. Every card must have a corresponding main-character entity. Unknown fields stay unknown. Card changes are surfaced for an explicit profile refresh; selected-opening changes automatically invalidate the baseline because that scene seed is no longer canonical.

The ordinary greeting is initialized once, then receives a checkpoint without being processed as a second event. Later selected assistant turns receive scoped state updates: world plus relevant existing entities and new directly established entities. Model outputs cannot supply canonical message IDs: `preserve` copies prior data and provenance; `update` receives the current assistant ID in backend code. Exact unchanged entities retain their previous sources even if the provider labels them updated. Omitted entities remain persistent, and out-of-scope existing entities cannot be updated. Controller roles cannot change, and user internal fields must stay unknown.

## Temporary setup panel

Before first-time baseline extraction, the backend appends one temporary system message with `metadata.story_continuity_notice:{version:1,status:"choice"}` and waits for an explicit Import/Create selection. It may update that row to `generating` or `failed`, using fixed public text without extracted facts or error diagnostics. After a valid baseline is saved or imported, the backend deletes the managed setup messages and clears `setupNoticeId`; it never writes a `ready` completion row. Optional envelope fields `initializationMode`, `awaitingSetup`, `setupNoticeId` and `setupNoticeShown` persist the user's Create decision, waiting state, temporary control target and deletion-respecting creation marker. Existing baselines/revisions imply previous authorization during normalization. Canonical schema 2 and portable format 1 remain unchanged.

`story_create_setup` serializes and validates the user's choice before scheduling extraction. No message event, status refresh or interceptor implicitly chooses creation for an uninitialized chat. Import retains its separate validated metadata anchor and restores locally without an extraction call. The frontend receives `canCreate`, `canImport`, `awaitingSetup` and `setupNoticeId`, then attaches extension-owned buttons with descriptive instructions to the temporary message via `ctx.dom.inject`. Render events handle a message initially outside the virtualizer viewport; the host preserves attached controls/listeners across remounts. `uninject` retires the whole control/instruction group after readiness or chat navigation. Drawer controls remain available when inline rendering is unavailable. Both entry points call the same import/create handlers, preserve file-picker user activation, disable duplicate actions while pending, and discard picker/results from an old chat. Backend diagnostics stay in the drawer; inline feedback remains generic. Begin Story uses the supported `triggerGeneration` append option.

A committed baseline permits removal of legacy ready/interrupted setup notices without another model call, revision change or checkpoint rewrite. Cleanup targets extension-marked initialization rows and excludes the import recovery anchor. Rebuilds reuse an existing pending row; initialized chats do not receive a new row solely on upgrade. Specialized, disabled and permission-blocked chats do not create a notice. Failed/canceled file selection leaves the choice intact, and a deleted choice notice remains deleted while drawer actions still work.

Notice messages are excluded from greeting selection, eligible assistant turns, user-turn association, specialized-card marker detection and prefix fingerprints. Completion/status edits therefore do not invalidate checkpoints or become narrative events. Branch matching resolves the target message by identity before comparing narrative prefixes, allowing deletion of a preceding notice during tracking without rejecting otherwise valid output. Forks retain copied notice metadata while canonical state and provenance inheritance continue to use only actual tracked turns.

The roleplay interceptor strips notice rows by extension metadata or host source-message identity, including when tracking has failed or is disabled. A worker-local ID registry also filters deleted notices from prompts assembled before cleanup. Fixed-text matching retains legacy choice/ready text support and preserves user-authored text. Lumiverse's hidden flag excludes recall embeddings while a setup row is pending; explicit filtering removes it from linear history. Notice updates skip chunk rebuilding. Message event handlers ignore managed writes/deletions so panel cleanup cannot queue recursive initialization or retries.

Panel I/O is best effort and never gates an authorized Create/import operation. Cleanup rereads the transcript, respects user deletion and never recreates a completed panel. A failed removal retries on a later enabled reconciliation while validated state remains available. Once a profile exists, later history-tracking failures stay in the drawer and do not retain the setup panel. The envelope remains version 1 with backward-compatible optional startup fields.

The floating widget is gated by active chat, widget preference and specialized-card routing rather than snapshot presence. Its first status can therefore render the icon before extraction. Subsequent chat navigation uses the known preference while loading that chat's status. Waiting, processing, ready and attention states update the same widget; Home, preference-off, chat changes and unload clean up the previous instance. Late status responses from another chat cannot change its state.

The chat widget uses the same 48 × 48 chromeless host dimensions and 32 × 32 SVG dimensions as Image Browser. Its full-size button contains a separate filled, gradient book SVG; the drawer retains its existing line icon. An extension-scoped SVG gradient ID avoids collisions with other extensions. A small status badge supplies state color without recoloring the artwork; only the processing badge pulses. Hover and keyboard focus follow the reference widget's interaction treatment, with reduced-motion overrides. This adds no runtime dependency on Image Browser or external image assets.

## Model identity protocol

The backend derives a typed alias registry from source-card order and the complete canonical collections before selection. Card characters use `c1`, NPCs `n1`, user characters `u1`, places `p1`, relationships `r1`, objectives `o1`, and lore sources `l1` (subsequent identities increment each prefix). Selecting or focusing a different actor does not renumber the registry. The registry is local to the request and rebuilt for future requests; no model-supplied alias map is trusted or persisted.

Initialization sends aliased card/lore definitions. Routine tracking sends aliased selected state, references and the complete identity catalog. Imported profile refresh supplies aliased sources and baseline. Roleplay injection also encodes aliases before packing its JSON budget. Source message IDs and irrelevant raw card metadata are excluded, and known persistent entity IDs embedded in supplied text are replaced. The host's original card/history and explicit user-authored prompt templates remain under Lumiverse's control.

The catalog reserves every main-character alias before initialization and offers separate `new_n1`, `new_u1`, `new_p1`, `new_r1` and `new_o1` creation slots within collection limits. The model must use an offered slot with `action:update`, and newly referenced characters must be declared in the same response. Main-character creation is never offered; all source cards already have reserved identities. Catalog entries mark existing identities with `canUpdate`. Routine provider schemas enumerate selected and creation aliases for entity records, while character reference fields retain all valid existing/creation aliases. Reference-only identities stay in the catalog to prevent duplication but must be omitted as output records. A full, unselected collection uses `maxItems:0` with a nonempty typed ID enum. Initialization and profile refresh retain the complete identity schema.

Decoding rejects unknown/canonical IDs, duplicate aliases, incorrect entity types, role/controller mismatches, known character-name mispairings and dangling references before canonical materialization. The backend resolves valid existing aliases and allocates UUIDs for valid new entities, caching allocations across the single repair attempt. A repaired response cannot reference a creation omitted from that response. Character/place aliases in descriptive fields are converted to names so stored prose does not depend on a request-local alias. Canonical validation, scope rules, provenance and branch checks then gate the commit. Invalid output is never partly saved. Alias validation cannot detect every semantic misassignment to another valid alias; extraction accuracy still depends on the model.

Canonical schema 2, storage envelope 1 and portable format 1 stay unchanged. Saves, mirrors, imports, exports and fork inheritance use persistent identities. No data migration or tracker replay is needed solely to adopt aliases.

## Profiles and per-request context

Schema v2 adds `relationshipContext` and `boundaries` to each private profile. Date Simulator's stable CASE/MAN/WOMAN/DISPOSITION/PREFERENCES/RELATIONSHIP/CURRENT CONTEXT/BOUNDARIES/INITIAL STATE coverage guides extraction: identity, background, disposition and voice, preferences, relationship history/agreements, boundaries, private durable facts, and the separate initial scene baseline. No fixed woman/man roles or dating-specific response vector is imposed.

Initialization and explicit refresh see the full bounded sources. Routine tracking sees complete selected state records (including their extracted profiles), identity-only catalog entries, the completed interaction, and at most 6,000 characters of targeted source excerpts. Local keyword/topic matching ignores actor-name-only matches, already covered profile facts, unselected card owners, examples/creator guidance, and the original opening. Long source passages produce explicitly partial windows. Retrieval is heuristic; missing matches retain uncertainty rather than creating facts. Source data is treated as reference, and established narrative changes take precedence over baseline descriptions.

Place selection includes names/IDs in the scene and selected characters' positions. When a location has no direct named match, its non-prepositional words must all match one saved place's name/description before that place is included. Numeric qualifiers remain significant, ambiguous matches are omitted, and connections/private/current facts do not supply location evidence. Selection only retrieves committed records; it does not change presence or canonical facts.

An imported setup's explicit refresh extracts from its frozen sources with the imported baseline supplied. Backend code accepts only previously unknown stable profile fields from that result; existing profile facts, appearance, world/current state, relationships and objectives remain recorded. A changed profile baseline invalidates tracker checkpoints for replay, while the imported physical starting scene and anchor remain authoritative.

The roleplay projection uses the same entity selection but has a 24,000-character JSON budget. It preserves the focused actor, user, mentions, colocation, active relationships/objectives and current/mentioned places when relevant. Identities and current scene/physical facts take priority when filling the budget, followed by stable profiles, internal state and appearance. Whole leaf values or records are omitted when they do not fit; canonical storage is never truncated. Omission metadata and prompt instructions explicitly distinguish selection/budget omission from unknown facts. The original host card/history remains separate from the extension's projection.

## Transactions and branches

Each chat has an independent serialized queue and storage file under the extension's `chats/`. Safe filenames combine a normalized chat token with a fingerprint, avoiding collisions from normalization alone. A checkpoint records its selected assistant ID/swipe, complete prefix fingerprint, validated state, and commit time.

Reconciliation reuses only a contiguous checkpoint prefix. Edits, swipes, deletion, or invalid provenance cut reuse at the first unproven turn. The current state is reset to that prefix before another generation runs, so failed output cannot resurrect a discarded tail. Every generated result is checked against a reread of the selected transcript before commit. Initialization additionally rereads card/opening sources. Revision and revision timestamp change together only when a new baseline/checkpoint commits.

Fork inheritance reconstructs the copied source prefix from Lumiverse's `messageIdMap`, accepts only matching checkpoints, remaps all source IDs and checkpoint keys to the branch, and excludes later source turns. Missing or invalid maps trigger ordinary reconstruction instead of guessing. Imported baseline sources and frozen initial state are remapped too. A confirmed chat deletion queues exact-path sidecar removal after pending work, and a tombstone prevents later writes from recreating it.

## Setups and authority

Portable format 1 is `{format:"story-continuity-initial-setup",version:1,sources,initialState}`. Every exported source ID uses `initial-setup`. File size, field shape, source card identities, canonical state, and source references are validated before import. The assistant anchor's neutral content, active swipe, and `metadata.story_continuity_setup` establish authority; its metadata is included in branch fingerprints. A valid import restores locally without tracker generation. Removing that anchor resets the imported epoch. Begin uses append-and-generate outside the continuity queue and is observation-only.

## Privacy, failure, and budgets

Canonical schema-v2 state and the private `story_continuity.state_v2` mirror remain complete. The older `state_v1` mirror projects the original five-field profile for compatibility. Stored v1 baselines/checkpoints and imported v1 setups upgrade conservatively during validation; new fields start as unknown, existing facts/provenance survive, and no model call or revision increment is needed solely to upgrade. The storage envelope and portable format remain version 1; exported state uses schema 2. The `story_continuity.public_v1` mirror and default drawer omit profiles, private facts, internal state, private relationships, boundaries, objectives, and source IDs. Opt-in private inspection returns complete canonical state. Private facts are supplied selectively to the roleplay model with explicit knowledge and output boundaries. These boundaries are model guidance, not an encryption or access-control mechanism against the owner.

Structured output is checked for exact keys, leaf types, enums, bounds, duplicate identities, dangling references, unsafe managed markup, user-role changes, and provenance. Invalid output receives at most one repair; failure retains the proven prior checkpoint and reports attention. Quiet original and repair requests share a timeout, and each reconciliation has a bounded overall budget. Long catch-up can resume from completed checkpoints.

Exact unchanged records labeled `update` are safe no-ops even outside selection and retain provenance. All genuinely changed out-of-scope records are collected in a typed scope error before materialization; repair feedback names each alias and asks for their omission while keeping supported selected updates. A final validation failure has code `TRACKER_STATE_REJECTED`. For routine turns only, the optional envelope field `rejectedTurn` stores a bounded diagnostic and a signature covering the contract revision, user, source/epoch, full prior state, turn prefix/focus and generation settings. Matching background retries return the proven checkpoint and diagnostic without generation, including after worker restart. Explicit reprocessing/profile refresh or a changed request releases the pause. Later turns remain behind the rejected prefix; provider/network exceptions are not memoized. This adds no canonical schema or portable setup migration.

Home navigation is explicit. Background events update their originating chat but cannot change the selected frontend route; late status/setup replies are ignored after navigation. Private display and prepared downloads are cleared on chat changes. Setup picker and native Save As calls begin inside user clicks. Cleanup confirmation is scoped to the requesting user and expires; candidates are rechecked inside their chat queue before deletion.
